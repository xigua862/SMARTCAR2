## 一、角色分工

| | **军师（决策对话）** | **工人（执行对话）** |
|---|---|---|
| 只做 | 写文档（**数据 / 测量 / 参考 / 结论**）、调查、算术、定判据、给提案 | 照卡写代码、编译、烧录、跑测试、`commit` + `push` |
| 不做 | **不改代码、不烧录、不动车、不 commit** | 不擅自改判据/参数/方案；卡里没有的不动 |
| 产出 | 文档 + 提案 + 任务卡 | 代码提交 + 回报 |

## 二、★讨论流程（最重要的一条）

1. **先建临时文档，再讨论。**
   任何"问题 / 新想法 / 待验证的猜想"，**第一步先起一份** `文档\讨论-<主题>-<日期>.md`，**边聊边往里写**。讨论记录和结论都落在里面，聊完了才谈"要不要改正文"。
2. **一句话不触发大改。**
   用户随便一句话 ≠ 授权改正式文档。要动正文，先交一份"**要动哪几处**"的清单，等用户点头。
   （教训：10-02 曾因一句口述就想重排全篇，浪费一整轮。）
3. **数据没定，不改数字。**
   实测之前，所有数一律标 **「待实测」/「参考值」**；参考图、开源件、别人的车的数值**禁止**当真值写进正文。
4. **一次成型，不来回改。**
   正式文档的修订**攒够了一次性出**（例如 v1.8），不做 v1.8a / 1.8b 反复摩擦。临时文档才允许反复涂改。

## 三、改正式文档的三道门（缺一不可）

1. **有实测数据**（或官方出处 / 明确算术）
2. **用户拍板**（口头同意即可，但要留一句在修订记录里）
3. **写清出处**：这个数从哪来（实测 / datasheet / 官方 README / 算术推导）

## 四、硬纪律（全是踩出来的）

1. **尺寸口径先问"这个数是谁的"**——"板长 88"未必在说传感器板。
2. **估算值必须标"未实测"**，别让后来的自己当成测量值。
3. **外设接口不许臆测**（UART/I2C/SPI 要去查官方 README + 驱动源码）。
4. **开源包只抄算法判据，不抄机械尺寸**（标准车规格抄到微缩车上直接装不下）。
5. **军师错了公开撤销**，不许悄悄改数。
6. **大动作先报**：下单 / 切板 / 烧录 / 通电 / 大规模改文档 —— 先说一声。
7. **每改一步就 commit**；commit message 用 **ASCII**（PowerShell 中文会乱码）。军师只写文件、不提交；**提交归工人**。
8. **项目隔离**：只动本项目（B 车不许串 A 车的结论/引脚/参数）。
9. **回答风格**：**结论先行 + 厚实质**——每个结论都要带算术或出处；不绕圈，也不短到没料。

## 五、用户画图习惯（给"画板/给数据"类任务用）

- SW 里用 **Y = 长边、X = 宽、X = 0 是对称轴**（对应文档里的 x/z 要换算）
- 习惯**先画对称轴、只画一边再镜像** → 给数据**只列半边坐标**
- **不懂工程符号**：φ（直径）、R（半径）、M（公制螺纹，M3 配 φ3.2 过孔）第一次出现要附人话解释
- 要的是**能直接照抄的数据表**（逐项坐标/孔径 + 自检阈值 + 易错点），不是概念解释
