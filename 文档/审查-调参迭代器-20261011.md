## 1. 必须改（5 条 · 不报错、只在实车/赛道现形）

### M1. 串口写参数无回读校验，且 `push_all` 吞掉失败返回值 —— "以为写进去了其实没生效"【已证实】

- **位置**：[调参迭代.py:330-333](file:///c:/Users/asus/Desktop/test16/脚本/调参/调参迭代.py#L330-L333) + [调参迭代.py:636-639](file:///c:/Users/asus/Desktop/test16/脚本/调参/调参迭代.py#L636-L639)
- **代码原文**：
  ```python
  def set(self, key, val):
      self._send("SET %s %s" % (key, fmt_val(val)))
      line = self._readline(time.time() + self.cmd_timeout)
      return bool(line) and line.upper().startswith("OK")   # 只等 OK，不回读
  ...
  def push_all(self):
      for k in FIRMWARE_KEYS:
          if k in self.p:
              self.guard.guarded_set(self.tp, k, self.p[k])  # 返回值被丢弃
  ```
- **为什么**：用户口述契约明确要"SET/GET/RUN + **回读确认**"。现状是：①`set` 收到 `OK` 就信，不 `GET` 回读，固件浮点截断/解析成别的值永远发现不了；②超时/丢帧/`ERR KEY` 时 `set` 返回 `False`，但 `push_all` 不检查，**静默继续 RUN**，车带着旧参数跑而脚本以为是新参数。这是最典型的"实车才现形"隐患。
- **最小改法**：
  ```python
  def set(self, key, val):
      self._send("SET %s %s" % (key, fmt_val(val)))
      line = self._readline(time.time() + self.cmd_timeout)
      if not (line and line.upper().startswith("OK")):
          return False
      got = self.get(key)                       # 回读校验
      try:
          return abs(float(got) - float(val)) <= abs(float(val)) * 1e-6 + 1e-9
      except (TypeError, ValueError):
          return False

  def push_all(self):
      for k in FIRMWARE_KEYS:
          if k in self.p and not self.guard.guarded_set(self.tp, k, self.p[k]):
              raise RuntimeError("SET %s 失败(超时/ERR/回读不一致)，停车" % k)
  ```

### M3. `run(n)` 收不满圈时静默降级成"1 圈/0 圈结论"【已证实】

- **位置**：[调参迭代.py:643-647](file:///c:/Users/asus/Desktop/test16/脚本/调参/调参迭代.py#L643-L647) + [调参迭代.py:568-601](file:///c:/Users/asus/Desktop/test16/脚本/调参/调参迭代.py#L568-L601)
- **代码原文**：
  ```python
  recs = self.tp.run(laps)
  # 收到的圈数可能少于请求（串口超时等），据实评估
  ev = EvalResult(recs, self.meta)
  ...
  self.finished = n > 0 and all(r.ok for r in self.records)   # n=1 也算"完成"
  ```
- **为什么**：契约承诺"每档 2 圈取最差"。但串口超时/丢帧导致 `run(2)` 只回 1 圈时，`EvalResult` 照算：`worst` 取那 1 圈、`finished` 判 True、`score` 基于单圈——**静默变成"1 圈结论"，无任何警告/降级标记**。回 0 圈时 `worst` 全取 `default=0.0`，`check_abort` 判"0<20 没超阈"，被当成正常 REVERT。实车串口一旦不稳，整个判据基础就塌了还不自知。
- **最小改法**：
  ```python
  recs = self.tp.run(laps)
  if len(recs) < laps:
      self.say("  [警告] 请求 %d 圈只收到 %d 圈，本档判失败(不收不满圈)" % (laps, len(recs)))
      recs = []                      # 强制 finished=False, score=fail_penalty
  ev = EvalResult(recs, self.meta)
  ```

  self.score = float(m["w_line"]) * self.worst_line_p95 + float(m["w_ins"]) * self.worst_ins_p95   # 无 time

  ```python
  if ev.meets_gate and ev.time_ms < v_good_time * (1.0 - eps):
      v_good, v_good_time = v_try, ev.time_ms
  ```
  或在 `score` 里显式加 `w_time * time_ms` 项并把权重写进 JSON。

## 2. 建议改（5 条 · 不致命但会在实车放大）

### S1. `accept_eps=1%` 与实测圈间噪声 ~2.5% 同量级，安全裕度不足 2×【已证实】

- **位置**：[调参参数.json:38](file:///c:/Users/asus/Desktop/test16/脚本/调参/调参参数.json#L38) `accept_eps=0.01`、[34](file:///c:/Users/asus/Desktop/test16/脚本/调参/调参参数.json#L34) `lap_per_config=2`；判据 [调参迭代.py:773](file:///c:/Users/asus/Desktop/test16/脚本/调参/调参迭代.py#L773)
- **实测噪声**（从 `调参日志.csv` 同 snapshot 2 圈量出，详见 §4.2）：`ins_p95` 圈间波动最大 **2.47%**（round 5：6.887 vs 6.719），`line_p95` 最大 1.50%。传导到 `score` 约 1~2%。
- **为什么**：日志里 REVERT 正确拒绝了 0.44%~0.92% 的改善（round 16/26/28/32/36，5 次），但 ACCEPT 的改善也常只有 **1.4%~2.0%**（round 34/38/40），已在噪声边缘。合成噪声尚且如此，实车（温漂/电池电压/赛道不一致）只会更大，1% 阈值大概率追噪声。
- **最小改法**：`accept_eps` 抬到 `0.03`；或 `lap_per_config` 抬到 4 圈并把 `EvalResult.worst`（max 聚合）改成中位数，压方差。

### S2. `clamp_bounds` 的 `or` 陷阱：种子值为 0 时边界锚点漂移【已证实】

- **位置**：[调参迭代.py:540](file:///c:/Users/asus/Desktop/test16/脚本/调参/调参迭代.py#L540)
- **代码原文**：`base = float(self.seed.get(key, val)) or val`
- **为什么**：Python `0 or val` 返回 `val`（0 是 falsy）。若某键种子=0（如 `autorun=0`），`base` 会退化成"当前值"，每次调用边界 `[base*0.6, base*1.6]` 都跟着漂，**"以种子为锚"的钳位失效**。当前 `autorun` 不在 `PHASE_B_ORDER`/`PHASE_C_ORDER`，不会被 `propose` 触发，所以**现在不炸但脆**；将来把 `autorun` 纳入自动调就会中招。
- **最小改法**：`base = float(self.seed[key]) if key in self.seed else float(val)`，显式区分"种子是 0"和"种子缺失"。

### S3. `best.json` 把 sim/meta/fixed 键全写进去，不是"固件参数表"【已证实】

- **位置**：[调参迭代.py:900-904](file:///c:/Users/asus/Desktop/test16/脚本/调参/调参迭代.py#L900-L904)；产物 [调参参数_best.json:52-81](file:///c:/Users/asus/Desktop/test16/脚本/调参/调参参数_best.json#L52-L81)

- **最小改法**：`save_json(best_path, {k: self.best_params[k] for k in FIRMWARE_KEYS if k in self.best_params})`。

### S4. `straight_deg` 在代码白名单但不在契约 §2 参数表【已证实】

- **位置**：代码 [调参迭代.py:55](file:///c:/Users/asus/Desktop/test16/脚本/调参/调参迭代.py#L55)；契约 `待并入v1.9-清单` §2 表只列了 `straight_min`/`corner_margin`，**无 `straight_deg`**

### 4.2 判据有没有被噪声淹没（最关键）

**实测圈间噪声**（从 `调参日志.csv` 同 snapshot 的 2 圈量出，`lap_per_config=2`）：

| round | 调的键 | line_p95 两圈 | Δ% | ins_p95 两圈 | Δ% |
|---|---|---|---|---|---|
| 2 | BASE | 4.715 / 4.645 | 1.50% | 6.799 / 6.779 | 0.29% |
| 5 | kp_steer+3% | 4.654 / 4.634 | 0.43% | 6.887 / 6.719 | **2.47%** |
| 15 | look_mm+3% | 3.937 / 3.879 | 1.48% | 5.955 / 6.091 | **2.26%** |
| 25 | corr_ki+3% | 3.682 / 3.703 | 0.57% | 5.461 / 5.359 | 1.88% |
| 21 | k_gyro+3% | 3.632 / 3.640 | 0.22% | 5.985 / 6.037 | 0.86% |

→ **圈间噪声实测：line_p95 最大 1.50%，ins_p95 最大 2.47%**。`score = 1.0·max(line_p95) + 0.6·max(ins_p95)`，传导到 score 约 1~2%。

**参数响应 vs 噪声**（同键差 3% 的 score 变化）：
- 碗底：round 39→41，corr_kp +3%，score 6.5676→6.5920，**响应 0.37% < 噪声 2.47%**（分辨不出）
- 碗壁：round 40→39，corr_kp +6.2%，score 6.7919→6.5676，**响应 3.3% > 噪声**（能分辨）

**判据**：`accept_eps=0.01`（1%），`lap_per_config=2`，`worst` 用 **max 聚合**（578-579 行）。
- 日志实证：REVERT 正确拒绝 0.44%/0.45%/0.73%/0.88%/0.92%（round 16/26/28/32/36，5 次）——**"不追噪声"在合成数据上成立**。
- 但 ACCEPT 的改善也常只有 1.4%/1.6%/2.0%（round 34/38/40），**与噪声 2.47% 同量级**，安全裕度 < 2×。

**结论**：阈值 1% **没有被噪声完全淹没，但已在临界线上**。合成噪声（高斯、`sim_noise_ins=0.018`）尚且让 ins_p95 波动 2.47%，实车噪声（温漂/电池/赛道不一致/起步打滑）只会更大。**判定：合成数据上"勉强不追噪声"，实车上"大概率追噪声"**。最小修法见 S1（抬 eps 到 3% 或加圈数取中位数）。

## 5. 两条边界判断（用户点名要点明）

### 5.1 SimTransport 是合成/玩具模型 —— 42 轮收敛≠参数物理正确【已证实】

- **位置**：[调参迭代.py:190-290](file:///c:/Users/asus/Desktop/test16/脚本/调参/调参迭代.py#L190-L290)
- **机制**：`SimTransport` 的"真值最优点 = 载入时的种子车参"（201 行 `self.opt = {k: seed_params[k]}`），响应面是绕最优点的碗状惩罚 `dz=log(v/opt)`（221-226 行），噪声是播种高斯。`perturb_for_sim`（911-923 行）先把种子扰动 ±15%，再让坐标下降"找回去"。
- **一句人话警告**：
  > **42 轮收敛只证明"这台迭代机器能转、不追噪声、能停"，不证明"参数物理上正确"。** 合成模型的真值最优点就是你自己填进 JSON 的种子值——脚本只是把被扰动的种子又找了回来，等于"自己出题自己答对"。实车响应面不是这个碗：可能有多个局部极小、非单调区、迟滞、温漂、电池电压变化。**参数对不对，必须上台架/赛道用真实 LAP 行重跑才知道，别把 best.json 当成"调好了"。**
- **怎么验证（推测部分）**：拿一段真实 LAP 行用 `--replay` 跑（[392-418 行](file:///c:/Users/asus/Desktop/test16/脚本/调参/调参迭代.py#L392-L418) 已留接口），对比 sim 收敛点与 replay 表现是否一致；不一致即坐实"碗≠实车"。

### 5.2 SerialTransport 写参数后无回读校验 —— 超时/丢帧/异常下"以为写进去了其实没生效"【已证实】

- **位置**：[调参迭代.py:330-333](file:///c:/Users/asus/Desktop/test16/脚本/调参/调参迭代.py#L330-L333)（set 无回读）+ [636-639](file:///c:/Users/asus/Desktop/test16/脚本/调参/调参迭代.py#L636-L639)（push_all 吞返回值）
- **异常路径逐条**：
  | 场景 | 代码行为 | 后果 |
  |---|---|---|
  | 超时（`_readline` 返回 None） | `set` 返回 `False` | `push_all` 不检查 → **静默继续 RUN，车带旧参数跑** |
  | 丢帧（OK 丢了） | 同上 | 同上 |
  | 固件返回 `ERR KEY`（键不在白名单） | `line.startswith("OK")=False` → 返回 `False` | 同上，**且不区分"键错"和"超时"** |
  | 固件收到 SET 但解析成别的值（浮点截断） | 返回 `OK` → `set` 返回 `True` | **永远发现不了**，脚本以为写对了 |
- **结论**：用户口述契约的"回读确认"**完全未实现**。这是"不报错、只在实车现形"的头号隐患——串口一旦不稳，整个调参建立在"参数已生效"的假设上，而该假设无任何校验。
- **最小修法**：见 M1（set 后跟 GET 回读 + push_all 检查返回值、失败即 raise 停车）。

## 6. 总结：这个脚本现在能不能上实车？

**不能。** 离线策略验证（A 诊断 + B 坐标下降 + 安全阀 + 不追噪声）在合成数据上**勉强自证通过**，可以冻结留档（D1）继续当原型。但**接实车的半条命全是缺口**：

1. **参数写进去没有回读校验**（M1）——串口一抖，调参建立在"参数已生效"的幻觉上；
2. **连续失败不回退**（M2）——文档头承诺的安全阀是死变量，DNF 软失败裸奔；
3. **收不满圈静默降级**（M3）——"每档 2 圈取最差"会悄悄变成"1 圈定生死"；
4. **C 阶段目标函数没时间项 + C 从未跑过**（M4/M5）——"加速"阶段名不副实，二分/回退/触顶零验证。

**缺的临门一脚**（按优先级）：①给 `SerialTransport.set` 加 GET 回读、`push_all` 检查返回值失败即停；②把 `self.consec_fail` 接上 rollback；③`run(n)` 收不满圈判失败；④C-1 加时间门；⑤`p95_gate_mm` 调到能过闸的值复跑 `--sim --phase C`，重生成 best/curve 到 gate 一致。**这五条做完，才谈得上"接实车"；在此之前，best.json 里的参数只是合成碗的碗底，不是赛道的最优。**
